# GitHub 推送失败如何排查

> 整理日期：2026-09-30
> 状态：排查顺序已从真实案例提炼；具体报错仍需逐项判断

## 这篇解决什么问题

在 Codex 中修改了项目，但“写入 GitHub”或 `git push` 没成功。新手常把本地目录、Git 仓库、GitHub 权限和网络问题混在一起，导致不断重复登录或重新上传文件。

## 先分清四层

| 层次 | 要确认的事情 | 常见现象 |
| --- | --- | --- |
| 本地文件夹 | 项目路径是否还存在 | `No such file or directory` |
| 本地 Git | `.git`、分支和远端是否完整 | `not a git repository`、没有 remote |
| GitHub 权限 | 当前方式是否有仓库写权限 | `403`、`Resource not accessible` |
| 网络传输 | GitHub 连接是否稳定 | HTTP/2、连接中断、空响应 |

## 推荐排查顺序

### 1. 确认项目路径

先在 Finder 中确认项目根目录确实存在。浏览器仍显示本地页面，只能说明页面曾经加载过，不能证明磁盘上的文件夹仍在原处。

### 2. 确认它还是 Git 仓库

在终端进入项目目录后运行：

```bash
git status
git remote -v
git log -1 --oneline
```

正常情况下，应能看到当前分支、GitHub 远端地址和最近一次提交。如果提示 `not a git repository`，先检查是否进入了错误文件夹，以及隐藏的 `.git` 是否仍在项目根目录。

### 3. 分清连接方式

- **本地 Git**：电脑上的 Git 使用现有凭据提交和推送；
- **GitHub Connector**：Codex 通过 GitHub API 读取或操作仓库；
- **浏览器登录**：用于网页管理和授权。

其中一条通道没有写权限，不代表另外两条也不能使用。看到 `403` 时，先确认是哪条通道返回的错误。

### 4. 检查认证和远端

如果电脑安装了 GitHub CLI，可以运行：

```bash
gh auth status
git remote -v
```

确认登录账号就是仓库拥有者或协作者，远端仓库地址也没有写错。

### 5. 最后处理网络问题

只有前四步都正常、日志明确显示传输中断时，才把重点放在网络。先重试一次；若持续出现 HTTP/2 传输错误，可以针对该次命令尝试 HTTP/1.1。不要因为一次网络失败就删除 `.git` 或重新初始化仓库。

## 不要急着做的事

- 不要删除 `.git`；
- 不要在没核对远端前强制推送；
- 不要把下载 ZIP 当作保留 Git 历史的常规备份；
- 不要把 Connector 的权限错误理解为整个 GitHub 账号失效。

## 真实案例里发生了什么

“物光”案例同时遇到了旧路径不可用、Connector 写入返回 `403` 和 GitHub 网络传输中断。最终通过恢复本地仓库、核对远端和凭据，再使用本地 Git 完成推送。这个组合故障比较特殊，所以本文只保留可复用的排查顺序，不把当时的绕行命令当作通用答案。

## 如何提交求助信息

提交 Issue 时请附上：

- 你在哪一步失败；
- 完整报错文字，访问令牌需要打码；
- `git status` 的结果；
- `git remote -v` 中隐去用户名或私有地址后的结果；
- 使用的是本地 Git、Connector 还是 GitHub 网页。
